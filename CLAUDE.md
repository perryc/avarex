## Project

AvareX (package name `avaremp`) is a cross-platform pilot's electronic flight bag (EFB) written in Flutter. It runs on iOS, Android, macOS, Windows, Linux (Snap/Raspberry Pi), and web.

## Commands

```bash
flutter pub get                 # install dependencies
flutter run                     # run the app (add -d macos / -d linux / etc.)
flutter analyze                 # lint (flutter_lints ruleset)
flutter test test/              # unit tests
flutter test test/avidyne_test.dart          # single test file
flutter test integration_test/app_test.dart  # end-to-end test (needs a device/emulator)
```

### Simulating in-flight data

The app listens for external device data over UDP. Python scripts in `tests/` replay recorded data against a running app:

```bash
python3 tests/nmea_test.py tests/nmea_kbvy_taxi_rwy16.txt   # NMEA GPS fixes → UDP 49002
python3 tests/gdl90_test.py tests/adsb_dallas.bin           # GDL90 ADS-B traffic → UDP 43211
```

`nmea_*_gen.py` scripts generate synthetic NMEA tracks; `sim_runway_awareness.py`/`test_runway_awareness.py` exercise runway-crossing detection.

### Local Android build/install (fork)

This is a fork without access to the upstream Firebase project (`avarex-479ae`), and two required files are gitignored, so a fresh clone won't build until they exist:

- `lib/firebase_options.dart` and `android/app/google-services.json` — normally generated by `flutterfire configure`; here they are checked-in-locally placeholder stubs (package name `com.apps4av.avaremp`, dummy keys). `Firebase.initializeApp` failure is caught and ignored in `lib/main.dart`, so the app runs with cloud features (community, scheduler, AI chat, pro login) inert; all core EFB features work. Recreate the stubs if missing rather than running `flutterfire configure`.

Flutter is managed via FVM (`~/fvm/versions/3.44.1/bin/flutter`); plain `flutter` is not on PATH. The release buildType has no signing config (CI signs separately), so a built APK must be signed before install:

```bash
~/fvm/versions/3.44.1/bin/flutter build apk --release
export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home
/opt/homebrew/share/android-commandlinetools/build-tools/36.0.0/apksigner sign \
  --ks ~/.android/debug.keystore --ks-pass pass:android \
  --ks-key-alias androiddebugkey --key-pass pass:android \
  build/app/outputs/flutter-apk/app-release.apk
adb install -r build/app/outputs/flutter-apk/app-release.apk
```

### Releases

GitHub Actions (`.github/workflows/`) builds all store artifacts. Version lives in `pubspec.yaml` (`0.0.118+118`); Apple/Google use `x.y.z+build`, Microsoft requires a 4-part version ending in 0, and Snap has its own version in `snap/snapcraft.yaml`.

## Architecture

### State: singletons + ValueNotifiers

There is no Provider/Riverpod. `lib/storage.dart` defines `Storage()`, the app-wide singleton holding nearly all global state: GPS position stack, plan route, settings, data caches, and a large set of `ValueNotifier`s that screens subscribe to (`gpsChange`, `trafficChange`, `timeChange`, `themeNotifier`, ...). `Storage().init()` runs in `main()` before `runApp()` and sets up databases, Firebase, and caches. Periodic `Timer`s in Storage drive the app: ~100ms (drain GDL90/NMEA buffers), 1s (GPS fusion/time), and longer intervals for weather and area updates.

### External data flow (GDL90 / NMEA)

`lib/io/udp_receiver.dart` listens on UDP ports 4000 and 43211 (GDL90) and 49002 (NMEA) and appends raw bytes to buffers on Storage. `lib/gdl90/` decodes framed GDL90 messages (ownship, traffic, AHRS, FIS-B uplink) — traffic goes to `TrafficCache`, which computes closure/alert levels and audible warnings. `lib/nmea/` parses NMEA sentences for external GPS and also generates autopilot output sentences. Ownship position from GDL90, NMEA, and the internal geolocator GPS all feed one fused stack in Storage; the GPS source mode (Auto/Internal/External) decides which wins. `lib/avidyne/` discovers Avidyne IFDs over Wi-Fi and transfers routes to them.

### Data layer

Three sqflite databases via helpers in `lib/data/`:
- **main.db** — FAA data (airports, navaids, airways, airspace), downloaded from the server via the download screen; read-only in normal use.
- **user.db** — aircraft, plans, checklists, logbook, W&B; user-writable.
- **weather.db** — cached METAR/TAF/NOTAM/winds etc., refreshed periodically by `lib/weather/` caches.

`lib/data/db_general.dart` picks the sqflite backend per platform (FFI on Windows/Linux, WASM on web, native plugin on mobile). Chart/database downloads and unzips run in background isolates (`lib/chart/download.dart`).

### UI structure

`lib/main_screen.dart` hosts four bottom tabs — Map, Plate, Plan, Find (tab indices in `lib/constants.dart`) — plus a drawer. Everything else is a named route registered in `lib/main.dart` (`/download`, `/documents`, `/logbook`, `/ai`, `/community`, `/scheduler`, ...). `MainScreenState.gotoMap()/gotoPlate()/gotoPlan()/gotoFind()` are static helpers for cross-screen tab switching. Maps use `flutter_map` with chart raster tiles and many overlay layers.

### Firebase / cloud

Firestore backs the crowd-sourced features: airport businesses (`lib/business/`), pilot community groups (`lib/community/`), and aircraft scheduling (`lib/scheduler/`); rules are in `firestore.rules` and composite indexes in `firestore.indexes.json`. Firebase Auth handles login, `lib/ai/` calls a Gemini model via Firebase AI for flight-planning chat, and RevenueCat (`lib/services/`) gates paid features.

### Platform notes

Bluetooth SPP input and the `/io` screen are Android-only (gated by `Constants.shouldShowBluetoothSpp`). Windows ships a prebuilt `windows/sqlite3.dll`. `lib/main.dart` installs a custom `WidgetsBinding` that caps the image cache size so NEXRAD/chart tiles don't exhaust memory.
